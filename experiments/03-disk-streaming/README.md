# 03 · DiskInfer CPU 磁盘流式推理

验证 DiskInfer 的 CPU 按需读取机制能否在 macOS arm64 上运行，以及 arena 预算如何影响内存、读量和输出一致性。**状态：待验证；DiskInfer commit、兼容小 GGUF、macOS 构建／运行路径均未选定，没有实测代码或结果。**

[实验索引](../README.md) · [实验契约](../SPEC.md)

## 前提与输入

维护者主线为 macOS M5、32 GB 统一内存。Android 展示仅是动机，不是该环境已可运行的证据。本实验先做兼容性检查，再决定是否能进入运行阶段；不预设 Mellum 可被选定版本加载。

- 源码：按 [第三方源码说明](../../repos/README.md) 独立检出 [DiskInfer 上游](https://github.com/Horn-Studio/diskinfer-android)，选定并记录完整 commit、工作区修改与构建条件。
- 模型：先选 1B–3B 候选 GGUF，确认常规与流式路径均支持其架构和量化，再记录来源、版本与校验值。当前无已确定模型或下载路径，见 [模型说明](../../models/README.md)。
- 请求：使用 [固定文本输入](../01-mlx-baseline/prompts/README.md)，先用短上下文与固定生成预算验证路径；正式回答检查另确认上下文和预算足够。记录实际模板、分词、采样及 arena 条件。

## 入口：先消除阻塞项

当前不提供构建或运行命令：上游 Android 入口不能直接充当 macOS 操作步骤。先完成下列检查，将选定版本的真实命令、源码位置和日志写入运行记录；若无法推进，则以阻塞记录结束本轮，不虚构可运行 CLI。

1. 检查平台依赖与模型支持，找到元数据加载、张量偏移、`pread`、arena、淘汰策略和计算图回调的实际路径。源码观察标为源码阅读，不能作为“已经运行”的证据。
2. 在目标 Mac 上验证构建与最小加载／生成，保存完整日志。若研究绕过文件缓存，还须独立确认该版本在 macOS 上的实际文件读行为。
3. 确定 arena 约束和读取行为的可观测方法。若现有日志不足，先明确需要的插桩与采样工作；仓库目前未实现这些工具。

## 运行步骤与输出

1. 优先用相同版本和相同 GGUF 对比常规 CPU 加载和流式 CPU 加载；固定请求条件。若必须使用不同构建，列出差异，限制归因。
2. 从可执行的 arena 预算开始，再选择多个预算对照。保存实际 arena 峰值与约束证据、内存／系统压力、应用读量与设备读量，以及 prefill／decode 的耗时和输出；缓存条件不明时如实标记。
3. 同权重、同模板、贪心采样比较 token ID，保留完整结果或首个分歧；只能取文本时注明粒度。按 [人工检查说明](../01-mlx-baseline/prompts/README.md) 单独检查最终回答。
4. 输出为 [运行记录](../../benchmarks/run-template.md)、兼容性检查、构建／运行日志、arena 与读取证据、输出对照及指标汇总。重复次数和测量定义使用 [基准测量口径](../../benchmarks/README.md)，归档见 [实验索引](../README.md)。

## 验收与失败记录

- 可运行：macOS 上实际加载并生成，有可复现的版本、模型与命令。
- 回答与一致性：小模型常规／流式输出对照可检查；最终回答检查与 token 一致性分开报告，出现分歧保留条件而非直接宣判算法错误。
- 机制：实际观察到流式读与 arena 预算约束。只跑常规模式、只观察到进程启动或较低 RSS 均不算机制通过。
- 性能：只有完成上述对照和测量才能讨论预算的代价／收益；小模型成功不证明大模型或 Windows 可行。满足机制和正确性检查后再尝试更大的 GGUF。

平台依赖无法移植、模型／量化不支持、无法观测 arena 或读量、OOM、读失败、截断与输出分歧均是有效记录。按 [失败记录指引](../README.md#输入产物与失败记录) 保存所选候选、错误、已完成步骤与未测项；若 commit 或模型仍未选定，就明确停留在该状态。Windows 的独立研究见 [Windows 入口](../../docs/windows-validation.md)，不由 macOS 结果代证。
